About this project

Why this portal exists

Project objective

This portal is a hands-on academic project for the Internet Programming lab. Instead of separate disconnected demo files, every syllabus topic is wired into one working student portal: registration, a quiz, search, and live data feeds.

What you can actually do here

  1. Fill out and submit the registration form to a PHP + MySQL backend
  2. Take a 10-question quiz that is scored and stored in the database
  3. Search student/course records live via AJAX (no page reload)
  4. Watch a course catalogue load from an XML file into cards
  5. Call a JSON web-service endpoint and see the raw response

Technologies used

  • HTML5
  • CSS3
  • Vanilla JavaScript (DOM, AJAX, JSON)
  • PHP 8
  • MySQL
  • XML + XSLT concept

Key terms

AJAX
Asynchronous JavaScript And XML — fetching data from the server without reloading the page.
DOM
Document Object Model — the live tree of elements JavaScript can read and modify.
API
Application Programming Interface — here, a PHP endpoint returning JSON.

Client ↔ Server, in one picture

Every AJAX feature on this page follows the same round trip:

  1. Client — browser JavaScript builds a request
  2. HTTP Request — sent to a PHP file on the server
  3. Server — PHP validates input, queries MySQL
  4. HTTP Response — PHP echoes a JSON string
  5. Client — JavaScript parses JSON and updates the DOM

What happens when you press Register

  1. JavaScript intercepts submit, runs client-side checks (UNIT II)
  2. fetch() sends a POST request to php/register.php (UNIT V AJAX)
  3. PHP re-validates and sanitizes every field (UNIT III server-side validation)
  4. PHP inserts the row using a prepared statement (UNIT III MySQL)
  5. PHP echoes a JSON success/error object (UNIT IV/V JSON)
  6. JavaScript reads the JSON and shows a message — no reload
Note for evaluators: if PHP/MySQL is not running (e.g. viewing this as static HTML), the form still runs full client-side validation and shows a simulated response so the demo remains visible.

XML, XSLT and feeds — concept notes

Raw XML structure

<courses>
  <course id="IP101" level="core">
    <title>Internet Programming</title>
    <duration>60 hrs</duration>
  </course>
</courses>

id and level above are XML attributes; <title> and <duration> are elements. A well-formed document plus a schema/DTD gives you XML validation.

XSLT & RSS/Atom, conceptually

XSLT (xml/courses.xsl) is a stylesheet language that transforms XML into HTML/plain text on the server or in a capable browser — the same idea as CSS, but for restructuring data rather than just styling it.

RSS/Atom feeds are just XML documents with a fixed vocabulary (<item>, <title>, <pubDate>…) that feed readers poll periodically — our courses.xml mirrors that pattern.

SOAP & WSDL — concept only

This project uses a lightweight REST-style JSON web service, because that is what modern browsers and PHP handle natively. The older SOAP style is included here only as a concept comparison, since it still appears in the syllabus:

AspectREST (used in this project)SOAP (concept only)
Data formatJSONXML (strict envelope)
ContractInformal (URL + params)WSDL file describes every operation
TransportPlain HTTP GET/POSTUsually HTTP, wrapped in a SOAP envelope
Typical useWeb & mobile appsEnterprise/banking integrations

A minimal SOAP request would look like this (shown for concept only — not executed):

<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Body>
    <GetStudent xmlns="http://example.org/ip">
      <StudentId>1</StudentId>
    </GetStudent>
  </soap:Body>
</soap:Envelope>
